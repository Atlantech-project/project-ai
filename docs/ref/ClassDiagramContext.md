## 0. How to read this file

### 0.1 System in one paragraph
ATLANTECH is a seaport operations platform (Egypt-only, 11 seaport governorates). A **Central SaaS** database handles licensing and billing for many ports. Each port runs its own **Port DB** (operational data: users, berths, terminals, yards, berthing requests, BAPLIE manifests, environment forecasts, AI recommendations, operational plans, dispatch, execution feedback, ML learning). The two databases are separate. **No foreign key crosses the boundary.** Only the signed licence token and statuses travel, always on a port-initiated check-in or as a manual token file. Cross-database links are "logical, no FK".

### 0.3 Notation conventions (all diagrams)
- Mermaid `classDiagram`. Stereotypes: `<<entity>>` table class, `<<ref>>` ghost class (PK only, defined in another diagram), `<<enumeration>>`, `<<mobile-local>>` (phone local DB, not a table).
- Level: hybrid. SQL-accurate physical columns only (no invented columns), key operations, status enumerations. Uses UML target values (state machines SM-1..SM-6, Master Context 7.4).
- Attribute tags: `PK`, `FK`, `UQ`, `GEN` (generated column), `DERIVED` (no column, computed). Boolean = `tinyint(1)` shown as boolean.
- Relationship legend: solid line = FK association (label = FK column, `+` = composite FK); filled diamond `*--` = composition (child lives and dies with parent, inferred from lifecycle/composite FK); dashed arrow `..>` = FK to a ghost class, a join table to a ghost, a logical link across databases, or a rule with no FK.
- Uniqueness-helper generated columns (e.g. `active_key`) are hidden from classes and described in notes.
- Pure join tables (only two key columns, not referenced elsewhere) are drawn as many-to-many associations. Two-key tables referenced by other tables stay as classes (BerthTerminal, TerminalCargoType).
- Reference/master data classes have no operations. Operations are traced to AD (activity), SM (state), Seq (sequence), FR (functional requirement), UC (use case) sources.
- Soft-delete philosophy: rows are never deleted; `is_active=0`, status INACTIVE, `revoked_at`, `active_to` are used instead.
- Names are aligned across UML, SQL and class diagrams (Master Context 7.4). Decisions: `Report_A_Accepted_SQL_Changes.md`, `Report_B_Tier3_Naming_Changes.md` (19 Oct 2026). FR IDs in open issues are the old numbering; operation traceability uses FRD v3.

### 0.4 Shared concept: licence, plan limits, READ_ONLY
Port-side `license_state` (singleton) drives mode SETUP / FULL / READ_ONLY. In READ_ONLY, creation/modifying actions return 423 `LICENSE_READ_ONLY`, but some actions are always allowed (returnForRevision, rejectAll, status updates, acknowledgements, safety exception, yard reject, TOS export, manual token upload). Plan limits (`max_terminals`, `max_berths`, `max_users`) come from the token and are enforced with 422 `PLAN_LIMIT_EXCEEDED` (Terminal.create, Berth.create, User.create, pilot/tug-master creation). These are logical rules, no FK.

### 1.4 Business rules
- One ACTIVE licence per port; `on_hold` = PENDING renewal held while current licence is SUSPENDED.
- Tokens signed lazily at check-in; refresh when 14 days or less remain.
- Check-in is always port-initiated; SaaS never pushes.
- Every transition is audited in the same transaction.
- SQL decisions applied: saas_admin.roles added; license.on_hold added; license.active_port_key generated + UNIQUE; billing_transaction.live_period_key; license_state.mode SETUP added; read_only_reason +3 values; license_state port_status, license_status, status_received_at added. Not added: token_iat, admin OTP/session tables, revoke_reason, status_reason, TLS certificate table.

### 7.2 End-to-end flow (how the classes cooperate)
1. SaaS: SaasAdmin onboards PlatformPortRegistry; issues License from LicensePlan; LicenseToken signed lazily at port check-in; BillingTransaction per period. Port's LicenseState stores token, mode, plan limits.
2. Port setup (2A/2B): Port Admin (PORT_GM) creates Users with UserRoleAssignment, Terminals, Berths (+BerthTerminal), pilots, tugs, shifts, SafetyConstraints, storage, yard, equipment, productivity profiles; plan limits enforced via LicenseState.
3. Request (2C): BerthingRequest (SUBMITTED) with BAPLIE upload/parse; Preliminary then Customs Approval; Part1Run builds EntryWindowProposal from ForecastRun + TidePredictionRun + congestion; staff confirms a FeasibleWindow (ENTRY_WINDOW_CONFIRMED).
4. Part 2 (2D): SolverRun produces Recommendation with ranked RecommendationOptions (AI or FIFO fallback); staff review/override; confirm OperationalPlan (request PLAN_CONFIRMED) creating PlanComponents (RESERVED); dispatch via assign + NotificationLog; for container terminals TerminalRecommendation (yard placement) after plan confirmation; cancel / delay re-plan loops use PLAN_CANCELLED and DELAY_REPLAN versions.
5. Execution (3): field app OutboxEvent → ActualStatusUpdate (idempotent, clock-skew flagged) → DeviationLog → possible delay re-plan; plan COMPLETED when pilot, tug, yard are DONE/NOT_APPLICABLE.
6. Learning (3): EvaluationMetric and DriftMeasurement on trusted data (MVP); RetrainingRun and MlModelVersion promotion are future work.

### 7.3 Status lifecycles (quick reference)
- License: PENDING→ACTIVE→(SUSPENDED↔ACTIVE)→EXPIRED/REVOKED (SM-1). Port: ONBOARDING→ACTIVE↔SUSPENDED→OFFBOARDED (SM-2). Port-side mode: SETUP/FULL/READ_ONLY (SM-3).
- BerthingRequest (SM-4): SUBMITTED ↔ NEEDS_REVISION; →PRELIMINARY_APPROVED→CUSTOMS_APPROVED→ENTRY_WINDOW_CONFIRMED→RECOMMENDATION_GENERATED→PLAN_CONFIRMED→COMPLETED; PLAN_CONFIRMED→PLAN_CANCELLED→re-plan; REJECTED / CANCELLED terminal.
- Plan components (SM-5): UNASSIGNED→ASSIGNED→STARTED→DONE; yard region YARD_PENDING→YARD_ACCEPTED→YARD_DONE or YARD_NOT_APPLICABLE.
- Outbox (SM-6): PENDING→SENDING→DONE or REJECTED (or back to PENDING).
