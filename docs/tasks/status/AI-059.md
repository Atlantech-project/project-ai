## PART2_SOLVE trigger handler (2026-11-22, `feature/AI-059-part2-solve-trigger-handler`, from `develop` `4a1663f`)

**Plan** (documented exception, as before): the design is the second `Proposed change` row of the AI-059 task decision. It was approved by the user's instruction of 2026-11-22 ("Implement the AI-owned handler using the existing project architecture … Create at least one meaningful end-to-end scenario test for every supported trigger").

**What it does** (`part2/job.py`, `part2/inputs.py`):
1. The runtime (AI-011) claims the run (QUEUED → RUNNING), so a re-delivered message is not handled twice. It retries technical errors once, and commits the handler's writes with the guarded `solver_runs` update or rolls all back and sends a FAILED C-06.
2. Scope from the CT-10 trigger entries; the horizon from the run's own `solver_runs` row; each REPLAN entry must name the request's CONFIRMED plan.
3. AI-050 snapshot → AI-060 B2 context → B3 per request (port-local date of the window, ACTIVE BAPLIE discharge ports, productivity profiles) → pins for REPLAN requests → AI-056 `handle_solve` (CP-SAT, FIFO on a technical failure) → AI-057 rationale → B4 per option (no forecast feed: NULL, DEC-21 rule 5) → AI-058 `plan_run` / `write_run`.
4. A request B3 can't time is `NO_FEASIBLE_PLAN` with `ENTRY_WINDOW` "No service time (B3): <reason>". The run outcome is recomputed.

**Nothing duplicated:** no solver, FIFO, rationale, persistence or snapshot logic is re-implemented. The new code is the orchestration, the B3 input reads and the outcome merge.
