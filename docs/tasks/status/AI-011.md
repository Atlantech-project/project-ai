## Deviation from an approved contract
**CT-08 §6 step 3, wrong-queue messages.** The step says to finish the run when `run_id` can be read. By the user's decision of 2026-11-03, a message whose `job_type` doesn't match the queue is instead logged at ERROR with `job_type`, `run_id` and queue, dropped, and never claimed. `run_id` belongs to the other job type's table: the worker has no grant there, and claiming the same number in its own table could fail an unrelated run. A `Proposed change` to CT-08 is on the PortHub branch below, awaiting the AI Team and Backend Team.

A message with no `job_type` at all isn't treated as a wrong queue, so step 3 applies to it.

## Review findings
**Independent review** by a separate subagent that hadn't seen the work, 2026-11-03: 1 Critical, 8 Important, 18 Minor. Each was checked against the code. The core guarantees held: atomic claim, guarded completion, C-06 only after commit. Fixes, each with a test:

| Finding | Severity | Fix |
|---|---|---|
| C1: `BLPOP` timeout equal to redis-py's default socket timeout could lose a popped message, and idle workers logged errors | Critical | `connect_redis` sets a 15 s socket timeout and is the default; integration test with the real client |
| I1: an exception on the failure path left the run RUNNING | Important | Rollback failure replaces the connection and retries; a failed retry count or C-06 build still ends the run FAILED; `worker_version` is checked at startup |
| I2: a database outage drained the queue | Important | The connection is opened before `BLPOP` |
| I3: a dangling `$ref` passed startup | Important | Every `$ref` is resolved at load |
| I4: `job_handling_failed` didn't say which job | Important | It carries `run_id`, `job_id`, `job_type` and `contract_version`; `job_failed` carries the reason |
| I5: EDI failures didn't write `result_detail.failure_reason` (CT-12) | Important | Written |
| I6: exception text could put a secret in logs | Important | Type and traceback location only |
| I7: `redis_for` ran outside the startup checks, printing part of a password | Important | Moved inside; Redis is also pinged |
| I8: a failed first settings read was never retried | Important | One retry before the limit is known |
| I9: failure-path test gaps | Important | `test_failure_paths.py`, plus new integration tests |
| M1 uncapped log values · M2 `run_id` 1.0 · M3 handler overriding C-06 fields · M4 any solver status · M5 swept solver run retried · M6 message over 1,000 characters · M7 `outcome` key on yard's failed detail · M8 misleading log event · M10 validation rollback and outage · M12 handler calling exit · M13 schema that isn't an object · M17 lock in the signal handler · M18 misplaced comment | Minor | Fixed |
| M9 yard handler must re-check its row (CT-11) | Minor | Documented in `common/README.md`, because handlers don't exist yet |

**Not changed, not blocking:**
- **M11:** a handler that commits or an autocommit factory leaves partial writes. Documented and accepted; AI-013 owns connections.
- **M14:** `contract_version: "1.0\n"` passes the schema's `$` pattern. Log-only effect, and the schema is a contract file.
- **M15:** a `run_id` beyond BIGINT logs as `job_not_claimed`, like a duplicate. Safe.
- **M16:** a wrapped MySQL 3819 wouldn't be recognised. Depends on AI-013's driver.
- **Remaining window:** if a connection dies between `BLPOP` and the claim, that one message is gone. It's logged with its ids, and the run stays QUEUED.
