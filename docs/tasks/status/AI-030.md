## Rulings made during implementation (deviations from the plan text)
- `unconverted` holds the whole element for measures (`KGM:ABC`, `x:CEL`), the code for stowage and full/empty (`12AB`, `7`), and the full segment text for repeats (`<field>#2`). The plan's examples mixed forms; the three shapes are documented in the `ParsedLine` docstring.
- Units other than `KGM` / `CEL` / `CMT`, and a non-integral weight or overhang, go to `unconverted`.
- Messages I chose for cases the plan didn't fix:
  - `"File is truncated: UNT is missing"`;
  - `"File is truncated: UNZ is missing"`;
  - `"UNH segment is missing"`;
  - `"File is corrupted: last segment is unterminated"` (an unterminated segment when `UNT`/`UNZ` exist).
- The "more than one `UNH`" check runs before the `UNT` count check; plan assumption 6 lists them the other way round. Each check rejects on its own, so the order matters only for a file with both faults.
- A shared test builder `tests/unit/edi/builders.py` is used instead of a helper inside `test_mapping.py`.
- `test_empty_elements_kept` corrected: in `EQD+CN+…+45G1+++5` the empty elements are `[3]` and `[4]`, not `[2]`.
- No commits, no worktree (CLAUDE.md, user memory). The progress ledger was kept in the session scratchpad, because `.superpowers/` is not git-ignored here.

**Critical, resolved by the user's decision: conflict with CT-12 v1.1 (Approved).**
- **The conflict.** CT-12 (`docs/ref/ATLANTECH_Contracts.md` line 793) says that "a different message type or a non-EDIFACT file → `REJECTED` with one ERROR issue: `segment_ref = "UNH"`, `message = "Unsupported BAPLIE version: <found>. Supported: SMDG 2.2.1 (D.95B), SMDG 3.1.1 (D.13B)"`". The parser had followed the AI-023 corpus oracles instead:
  - case 15: `segment_ref` `None`, `"File is not UN/EDIFACT"`;
  - case 17: `"Message type COPRAR is not BAPLIE"`.
- **How it was found.** The plan quoted the oracle texts but did not notice the conflict; the reviewer found it.
- **Decision.** The user chose option (a) on 2026-11-10: "Change both rejection messages to follow CT-12 exactly". For `<found>` on a non-EDIFACT file: the first 3 characters of the file as read, or `"none"` if the file is empty or has no readable characters.
- **Fix:**
  - `parser.py` (`_found_in_non_edifact`, the `WRONG_MESSAGE_TYPE` branch) and `mapping.py` (the old texts removed);
  - `test_not_edifact` (6 inputs, including the `none` cases) and `test_wrong_message_type` failed first (9 failures with the old texts), then passed.
- **Corpus.** Oracles 15 and 17 now disagree with the parser, and editing the corpus is outside AI-030. `test_corpus_parse.py` holds them in `CT12_OVERRIDES`: severity and code still come from the oracle, the issue from CT-12. `test_ct12_overrides_still_differ_from_their_oracles` fails once AI-023 corrects an oracle, so the override is removed rather than kept stale.
- **Interpretation (mine).** "As read" means the decoded text with a UTF-8 BOM removed and nothing else stripped, so `"  PK…"` gives `"  P"`. "No readable characters" means none of the 3 is a printable, non-space character. An empty or whitespace-only file never reaches this point: it is `UNREADABLE_FILE`.

**Deferred (Minor, not fixed):**
- A whitespace segment terminator declared in `UNA` (for example `\n`) is stripped and the file rejected; a released trailing space is lost.
- Under a decimal-comma `UNA`, a value written with `.` goes to `unconverted` rather than being accepted.
- `ParsedLine` is frozen but not hashable (it holds dicts).
- A file with `UNA` and no `UNB` is read, and `UNZ` is accepted before `UNH`.
- A `UNH` without a message identifier gives `"Message type  is not BAPLIE"` (empty type).
- A UTF-16 file is not decoded as such; it ends `NOT_EDIFACT`.
- Unknown tags outside `UNH`…`UNT` are not reported.
- Nine defensive parser lines are not covered: a repeat of an unconverted value, an empty port, IMDG or EQD component, and a second `TDT+20`.
